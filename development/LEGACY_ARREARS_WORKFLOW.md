# Legacy stall-owner baseline and verified arrears

The web application stores the December 1, 2026 computerized tracking baseline in `Profiling.StartDate` and marks its source with `IsLegacyBaseline`. The marker, rather than a date comparison, controls whether the occupancy month is billable. Newly created and imported profiles default to `IsLegacyBaseline = 0` and keep the existing next-month billing rule.

`BPLS_Dev.legacy-arrears.sql` is an idempotent, development-only schema migration. It creates the marker, period-based `StallOwnerArrears`, and `PaymentHistoryArrears`. The arrears table has a unique `(SIN, BillingYear, BillingMonth)` constraint, non-negative amount checks, verifier, timestamp, and Treasury reference. The link table keeps arrears distinct from `PaymentHistoryBilling`.

`BPLS_Dev.legacy-baseline-2026.sql` records the earlier guarded initialization of the reviewed 538-record cohort (`SIN-2026-0663` through `SIN-2026-1200`). That initialization was applied after direct user approval. Its preservation of four older unpaid bills was subsequently superseded by the approved clean reset described below. These one-time historical scripts must not be rerun against the renumbered cohort.

`BPLS_Dev.clean-baseline-preflight.sql` discovers scope, SIN references, collisions, financial counts, and deterministic name ordering. `BPLS_Dev.clean-baseline-reset.sql` performs the clean reset in one serializable transaction, with SQLCMD variable `ApplyReset=0` for rollback verification and `ApplyReset=1` for the authorized commit. The committed development reset removed the four pre-baseline regular bills, retained December bill IDs through transactional staging, cleared old financial state, and reassigned the exact cohort alphabetically to `SIN-2026-0001` through `SIN-2026-0538`. Sorting uses `FullName ASC, old SIN ASC` under the existing database collation. Structured audit SIN references follow the mapping; historical audit text is preserved. Foreign keys remain enabled. Exact comparisons protect unrelated profiles, users, rates, vehicle records, payments, bills and links. Any failed guard rolls back the operation.

`BPLS_Dev.clean-baseline-postcheck.sql` verifies the clean official state. The reset is a one-time operation for the old SIN population, not a startup task. Local database output, real owner mappings, detailed financial reports and backups are excluded from Git. The normal SIN allocator continues above the highest existing year-specific sequence, including protected development fixtures; it does not hardcode 0539.

The normal payment path runs in one serializable transaction. It locks the profile and outstanding regular and arrears rows, recomputes base rent, additional charges, and one 25% base-rent penalty per overdue period, inserts the OR/payment, links both obligation types, marks them paid, and writes the payment audit. Failure rolls back all changes. Adding or correcting unpaid arrears writes an audit entry but creates no payment. Report preview uses current saved data and remains read-only. The payment report requires a recorded OR.

The dashboard's **Unpaid Billing Periods** KPI remains a count of `MonthlyBilling` only. Collections remain derived from `PaymentHistory` and vehicle payment history. Verified arrears and printed reports do not increase collections.

Before any future production migration, identify and separately authorize the exact deployment cohort and cleanup policy, back up its records and existing bill/payment history, reconcile historical obligations with Treasury, and adapt the guarded scripts to that authorized cohort. Run preflight, review all SIN dependencies and collisions, then apply schema and data migrations with post-migration count and amount checks. Do not execute these BPLS_Dev-only scripts against production. No production connection or deployment is part of this work.
